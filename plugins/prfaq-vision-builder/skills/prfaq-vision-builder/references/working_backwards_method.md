# Working Backwards — method reference

Deeper notes on the method behind this skill. Read once at the start of a session; keep in working memory while guiding the user.

## Why the method exists
Standard planning tools — SWOT, market-sizing, pro-forma P&Ls, mockups, long spec docs — don't force deep enough thinking about the *user* and what would genuinely be valuable to them. The PR/FAQ was created as a forcing function: by writing the user's future experience as narrative prose first, you commit to clarity before committing resources. It is slow on purpose. The work done up front saves far more work later, and it kills weak ideas cheaply — on paper, before they consume a team.

## The five Working Backwards questions (the anchor)
Answer these before writing. Struggling to answer them is itself the signal that more thinking is needed.

1. **Who is the user?** Be specific about time, place, and situation. Force ~5 defining characteristics. This is not a marketing persona — the goal is to get user- and problem-centric.
2. **What is the user's problem or opportunity?** Name a specific problem; size it.
3. **What is the most important user benefit?** Prioritize one. Don't list ten.
4. **How do you know what the user wants or needs?** Evidence over intuition. Your own experience may not represent the user — name the actual signal.
5. **What does the user experience look like?** Concrete before → after.

## The three desired outcomes
A real vision satisfies three outcomes at once, not just one:
- **User outcome** — solves a real problem for the person using it.
- **Business outcome** — viable / worth it for the organization.
- **Builder outcome** — satisfies the people who'll build and maintain it.

There is no good solution that is viable for the user but not the business, or that nobody wants to build. For **internal tools** these three heavily overlap (the user, the business, and the builders are often the same team) — which is exactly why a single combined document works well. For **external products** keep them distinct and make sure the FAQ addresses all three.

## The press release — seven-paragraph shape
Written in present tense, as if the product already shipped and succeeded. Less than one page. Jargon-free. From the user's point of view.

1. **Headline** — the product's name and what it does, in one line a real user would say.
2. **Sub-headline** — who it's for and the single core benefit, one sentence.
3. **Summary paragraph** (with a dateline for flavor) — the whole thing in miniature; the reader should grasp the vision from this alone.
4. **The problem** — the painful before-state, concrete and specific.
5. **The solution** — how it works, in plain language; the problem, the solution, and why the user cares, unambiguously.
6. **Quotes** — an internal/leadership quote explaining *why this matters* to the organization, and a user quote describing how it changed their day. (Use fictional/representative names; never attribute invented quotes to real named people.)
7. **Call to action** — how the user gets started today.

**Litmus test:** if the press release doesn't make the reader want to use the product, it needs rewriting. Don't move on until it passes.

## The honest-competition discipline (the most common failure)
The biggest trap — especially for internal tools — is discounting the alternative. If the problem is real, the user *already has* some way of dealing with it today. There is always a current solution.

- **External:** name real competitors AND the status-quo behavior (doing nothing, a spreadsheet, a manual process).
- **Internal:** the "competition" is the current workaround — the manual process, the existing tool, the way it's done now.

Then answer honestly: is the new thing compelling enough that people will actually **change their behavior** and switch? "We're building it for ourselves" is not an exemption — if no one would switch from the current workaround, the vision is hollow. This question, asked early, is what catches weak ideas.

## The FAQ — what it's for
The FAQ makes the vision credible by answering the hard questions and giving a clear-eyed assessment of how expensive and challenging the thing will be. It's where feasibility, risk, scope, and "what has to be true" get pinned down. In this skill it stays lean and lives in the same document as the PR — but it is not optional. A PR with no honest FAQ is a wish, not a vision.

## Drafting order ≠ output order
Reason through the FAQ thinking **before** writing the press release, even though the PR appears first in the output. Sequence:
1. Establish the current state of the world (facts as they are today).
2. Work backward from the desired outcome — answer the hard questions and the user-facing questions.
3. *Then* write the press release.
This keeps the PR grounded in pressure-tested answers rather than wishful spin.

## The read-and-discuss meeting practice
The document exists to create alignment, and how it's reviewed matters:
- Circulate the doc; have attendees **read silently** (~15–20 minutes) at the start of the meeting.
- **Don't present it.** The written narrative is the whole point — it presents the reasoning cleanly and avoids the distortions of live pitching. Aim to spend the majority of the meeting *discussing* what was read.
- Frame it as **truth-seeking, not selling**, and **improving, not deciding**. Reviewers help refine the idea through debate; the goal is not a thumbs-up.
- It's a **living document**. Be *stubborn on the vision, flexible on the details*. Update it as feedback, pilots, and data come in.
- Expect most pressure-tested vision docs to change substantially, and some to be abandoned. That's the method working — deciding cheaply, on paper, where to invest.

## When to split
Keep one document for focused products and all internal tools. Split into multiple linked PRs only when there are **two genuinely distinct user types with different experiences** (the classic example: a marketplace with a seller PR/FAQ and a buyer PR/FAQ). If you detect two such users, offer to write two linked PRs rather than one overloaded document.
